# 입찰 적합성 분석 설계

## 1. 목적

기존 관리자 `입찰 공고` 상세에 회사의 참가 가능성과 예상 투찰 범위를 빠르게 검토할 수 있는 근거 중심 분석을 추가한다. 나라장터 물품 공고를 주 대상으로 하고 K-apt 공고도 확보 가능한 범위까지 분석한다. 결과는 자동 결정을 대신하지 않으며, 확인한 자료와 확인하지 못한 조건을 분리해 관리자가 원문 검토 우선순위를 정하도록 돕는다.

## 2. 확정 범위

### 2.1 포함

- 회사 입찰 자격 공통 설정
- 나라장터 물품 공고의 상세, 기초금액, 면허·지역 제한, 구매 대상 품목, 첨부문서 수집
- K-apt 공고의 API 상세정보와 공식 상세 페이지에서 직접 연결된 첨부문서의 제한적 수집
- PDF, HWP 5.x, HWPX, DOCX, XLSX의 텍스트·표 추출
- 요구 사양, 인증, 참가 조건, 가격 조건의 규칙 기반 정규화와 근거 문장 보존
- 전체 제품군 기준의 사양 충족도 계산. 개별 제품명 추천이나 제품별 매칭 결과는 표시하지 않음
- 최근 2년 나라장터 LED 관련 물품 개찰 결과의 최소 통계 데이터 백필 및 증분 수집
- 기초금액, 낙찰하한율, 공식 투찰 가능 범위, 통계 예상 투찰가와 신뢰도 표시
- `참여 추천`, `검토 필요`, `참여 어려움` 자동 상태
- 실패한 분석의 관리자 재실행과 분석 상태 표시

### 2.2 제외

- AI·LLM API를 이용한 문서 해석
- OCR과 스캔 이미지 본문 인식
- 첨부파일 원본 영구 저장
- 모든 투찰 참여 업체·사업자번호·전체 개찰 순위 저장
- 개별 사내 제품 추천 또는 공고별 제품 목록 노출
- 회사 원가, 마진, 생산 여력에 따른 수익성 판정
- 자동 투찰 또는 나라장터·K-apt에 대한 쓰기 작업

## 3. 용어와 표시 원칙

- `기초금액`: 예정가격 산정의 기준이 되는 공고 금액
- `예정가격`: 복수예비가격 중 추첨된 가격의 산술평균 등 공고별 방식으로 확정되는 낙찰 판단 기준
- `사정률`: `예정가격 ÷ 기초금액 × 100`
- `낙찰하한율`: 예정가격 대비 심사 대상이 될 수 있는 최저 투찰 비율. 공고 원문에 확인된 값만 확정값으로 사용
- `낙찰률`: `낙찰금액 ÷ 예정가격 × 100`
- `예상 투찰가`: 공식 계산 또는 과거 통계에서 얻은 참고 범위. 실제 낙찰가로 표현하지 않음

조달청은 국가계약법 적용 입찰의 복수예비가격을 보통 기초금액의 ±2%, 지방계약법 적용 입찰은 ±3% 범위에서 작성한다고 설명한다. 그러나 공고마다 산식, A값, 단가·총액 방식과 낙찰자 결정 기준이 다를 수 있으므로 문서에 명시된 산식이 일반 규칙보다 항상 우선한다.

## 4. 접근 방식

### 4.1 선택: 근거 중심 규칙 분석

공식 API의 구조화 필드와 첨부문서 텍스트를 결정적인 규칙으로 분석한다. 각 값에는 출처 문서, 쪽 또는 표 위치, 근거 문장을 연결한다. 해석할 수 없거나 서로 충돌하는 정보는 추측하지 않고 `확인 필요`로 남긴다. 별도 AI 환경변수와 호출 비용이 없으며 같은 입력에 같은 결과를 재현할 수 있다.

### 4.2 제외한 대안

- AI 중심 분석은 비정형 문장 대응 범위가 넓지만 외부 비용, 추가 secret, 재현성과 오판 근거 문제가 있어 초기 범위에서 제외한다.
- 수동 체크리스트만 제공하는 방식은 구현은 작지만 반복 검토 시간을 충분히 줄이지 못한다.

## 5. 아키텍처

기존 `tenders` 모듈 안에 수집, 문서 추출, 요구조건 정규화, 적합성 판정, 개찰 통계를 각각 독립 서비스로 추가한다. Redis나 별도 큐를 도입하지 않고 PostgreSQL의 영속 상태와 기존 `node-cron`, advisory lock을 재사용한다.

### 5.1 주요 컴포넌트

- `TenderEnrichmentService`: 관련 공고의 추가 공식 API 정보와 첨부 링크를 가져오고 분석 작업 상태를 관리한다.
- `TenderDocumentFetcher`: 허용된 공식 호스트의 문서를 제한된 크기와 시간 안에서 내려받는다.
- `TenderDocumentTextExtractor`: 파일 형식을 식별하고 형식별 어댑터로 텍스트·표를 공통 블록으로 변환한다.
- `TenderRequirementParser`: 수치 비교 표현, 인증명, 지역·업종·기업구분·직접생산·실적 조건, 낙찰 산식을 정규화한다.
- `TenderCompanyProfileService`: 관리자가 저장한 회사 자격과 유효기간을 조회·검증한다.
- `TenderSuitabilityAnalyzer`: 요구조건과 회사 정보·전체 제품군을 비교해 사양 충족도와 자동 상태를 계산한다.
- `TenderAwardCollector`: 나라장터 낙찰정보서비스의 LED 관련 물품 개찰 결과를 최근 2년까지 백필하고 이후 증분 수집한다.
- `TenderPriceAnalyzer`: 공식 계산 범위와 충분한 표본이 있는 통계 예상 투찰가를 계산한다.

각 컴포넌트는 provider-neutral 입력·출력 계약을 갖는다. HWP 파서나 공공 API 필드가 바뀌어도 요구조건·판정 계층은 영향을 받지 않는다.

### 5.2 처리 흐름

1. 기존 매시 공고 수집이 신규·변경 관련 공고를 저장한다.
2. 공고 fingerprint가 바뀌면 enrichment 상태를 `PENDING`으로 전환한다.
3. 출처별 추가 API와 첨부 링크를 조회한다.
4. 첨부파일을 메모리 또는 작업 전용 임시 파일로 처리하고 텍스트·표 블록과 hash만 저장한 뒤 원본을 삭제한다.
5. 요구 사양·인증·참가 조건·가격 조건을 정규화한다.
6. 최신 회사 자격 profile과 전체 제품군 snapshot으로 분석하고 analyzer version을 기록한다.
7. profile, 제품, 공고 또는 analyzer version이 바뀌면 관련 분석을 무효화하고 다시 계산한다.
8. 야간 작업은 개찰 결과를 증분 수집한다. 초기 백필은 월 단위 구간으로 나누고 호출 제한을 지키며 중단 지점부터 재개한다.

## 6. 출처별 데이터 전략

### 6.1 나라장터

현재 사용 중인 `조달청_나라장터 입찰공고정보서비스`의 물품 상세, 물품기초금액, 면허 제한, 참가 가능 지역, 구매 대상 물품 정보를 공고번호·차수로 추가 조회한다. 응답에 제공되는 규격서 URL만 첨부 대상으로 인정한다.

개찰 통계는 `조달청_나라장터 낙찰정보서비스`의 물품 개찰·낙찰 정보를 사용한다. 기존 `PUBLIC_DATA_SERVICE_KEY`를 재사용하지만 공공데이터포털에서 이 서비스에 대한 별도 활용신청 승인은 필요하다. 공식 base URL은 코드 기본값으로 두고 환경변수는 선택적 override만 제공한다. Railway 직접 호출이 기존과 같은 안전한 HTTP 200 이상 응답을 보이면 현재 Vercel relay의 호스트·operation allowlist를 낙찰정보서비스의 필요한 물품 조회로만 확장하며 기존 shared secret과 service key를 재사용한다.

### 6.2 K-apt

K-apt API가 제공하는 공고·낙찰 필드를 먼저 사용한다. canonical `k-apt.go.kr` 상세 페이지에서 같은 공고번호에 직접 연결된 첨부 링크만 제한적으로 해석한다. 로그인, CAPTCHA, 세션 우회 또는 범용 HTML 크롤링은 하지 않는다. 첨부 링크나 가격·참가 조건이 제공되지 않으면 해당 항목은 `확인 필요`다.

K-apt의 예정가격·낙찰하한율이 구조화되지 않은 경우 나라장터 공식을 대입하지 않는다. K-apt 통계는 기초금액, 예정가격, 낙찰금액의 동일한 세 값이 신뢰 가능한 형태로 확보된 공고만 사용하며, 그렇지 않으면 공식 계산과 통계 예상가를 모두 숨긴다.

## 7. 문서 추출

### 7.1 지원 형식

- PDF: 텍스트 layer와 표 순서를 추출한다. 이미지 전용 PDF는 `OCR 필요`로 표시한다.
- HWPX: ZIP 내부 OWPML XML에서 문단과 표 cell을 문서 순서로 추출한다.
- HWP 5.x: CFB/OLE2 FileHeader와 BodyText section을 읽고 압축 문단과 표 record를 추출한다.
- DOCX: OOXML 문단과 표를 추출한다.
- XLSX: 표시값 기준 sheet·행·cell을 추출하고 숨김 sheet 여부를 근거 metadata에 기록한다.

HWP/HWPX는 Node 20을 지원하는 `hwp-convert` 1.13.x를 `HwpDocumentExtractor` 어댑터 뒤에서 사용한다. PDF는 `pdfjs-dist`, DOCX는 `mammoth`, XLSX는 `exceljs`를 각각 형식별 어댑터 안에서만 사용한다. 정확한 버전은 lockfile에 고정하고 실제 공개 샘플과 저장된 fixture가 모두 통과해야 활성화한다. 외부 프로그램 실행이나 네트워크 변환 서비스는 사용하지 않는다. 암호화·배포용·손상·미지원 구형 HWP, 비정상 archive, 이미지 전용 문서는 실패 원인을 정규화하고 다른 문서 분석을 계속한다.

### 7.2 보안·자원 제한

- HTTPS만 허용하고 나라장터·K-apt 공식 host allowlist 밖 redirect를 거부한다.
- URL은 API 응답 또는 같은 공고의 canonical 상세 페이지에서 얻은 값만 사용한다.
- 파일당 다운로드 상한 20 MiB, 추출 텍스트 상한 10 MiB, 문서당 처리시간 상한 15초를 적용한다.
- MIME header만 믿지 않고 magic byte와 container 구조를 함께 확인한다.
- ZIP/CFB entry 수, entry별·전체 압축 해제 크기와 압축비 상한으로 archive bomb을 차단한다.
- 파일명, URL query, 문서 원문, API 원문 오류는 일반 로그에 남기지 않는다. 로그에는 공고 ID, 형식, 단계, 안전한 오류 코드만 기록한다.

## 8. 회사 입찰 자격 설정

관리자 JWT 아래 단일 company profile을 제공한다.

- 회사명과 사업자번호
- 본점 소재 시·도와 시·군·구
- 나라장터 조달업체 등록 여부와 공급물품 분류번호
- 등록 업종·면허 코드, 명칭, 유효기간
- 중소기업·소상공인 등 기업구분과 확인서 유효기간
- 직접생산확인증명 세부품명번호와 유효기간
- 보유 인증과 유효기간. 기존 인증서 데이터와 연결하거나 profile에서 추가 가능
- 동종 물품 납품실적의 기간·금액 범위. 자동 증빙이 없는 항목은 `관리자 입력` 근거로 표시

저장 시 유효기간과 중복 코드를 검증한다. profile 변경은 version을 증가시키고 모든 활성 공고 분석을 재계산 대상으로 만든다. 만료된 자격은 보유로 판정하지 않는다.

## 9. 분석 규칙

### 9.1 사양 충족도

공고에서 구조화할 수 있는 요구 사양을 `필수`와 `참고`로 구분한다. 전체 제품군 안에서 각 요구값을 충족하는 등록 제품이 하나 이상 있는지를 계산하되 제품명은 결과에 노출하지 않는다.

- 필수 사양 가중치 2, 참고 사양 가중치 1
- `충족도 = 충족 가중치 ÷ 비교 가능한 전체 가중치 × 100`
- 확인할 수 없는 항목은 분모에서 제외하되 `확인 필요 N개`와 `분석 범위 X/Y`를 반드시 함께 표시
- 서로 다른 제품의 속성을 하나의 가상 제품처럼 합쳐 완전 충족으로 표현하지 않는다. 동일 조달 품목 단위 안에서는 단일 제품 snapshot이 충족하는 조합을 기준으로 하고, 여러 조달 품목 공고는 품목별 결과를 합산한다.
- 비교 가능한 요구 사양이 없으면 퍼센트를 만들지 않고 `계산 불가`로 표시

이 계산은 내부적으로 제품 snapshot을 비교하지만 개별 제품 매칭·추천 UI와 제품명은 제공하지 않는다.

### 9.2 인증과 참가 조건

인증, 지역, 업종·면허, 기업구분, 직접생산, 나라장터 등록, 실적 조건을 각각 `SATISFIED | UNSATISFIED | UNKNOWN`으로 판정한다. 공고의 `필수`, `해야 한다`, `이상/이하`, 제한 코드 등 명시적 표현만 hard requirement로 취급한다. 문서끼리 충돌하면 최신 정정공고의 구조화 필드를 우선하고 충돌 사실을 보여준다.

### 9.3 자동 참여 상태

| 상태 | 기준 |
| --- | --- |
| `참여 추천` | 필수 조건 불충족이 없고 필수 인증을 모두 보유하며 사양 충족도 80% 이상 |
| `검토 필요` | 확인 필요 항목이 하나 이상이거나 사양 충족도 50~79% |
| `참여 어려움` | 필수 참가 조건·필수 인증이 명확히 불충족이거나 사양 충족도 50% 미만 |

확인 필요 항목이 있으면 조건을 충족한 것으로 간주하지 않는다. `참여 추천` 조건과 `검토 필요` 조건이 동시에 성립하면 `검토 필요`가 우선하며, 명확한 필수 불충족은 항상 `참여 어려움`이 우선한다. 마감된 공고는 적합성과 별도로 `마감` 상태를 표시한다.

관리자는 분석 결과를 수정하지 않고 `검토 완료`와 내부 메모만 남길 수 있다. 자동 결과를 사람이 덮어쓰면 근거와 알고리즘 변경 이력을 잃으므로 초기 범위에서 override는 제공하지 않는다.

## 10. 가격 분석

### 10.1 공식 계산

공고에서 기초금액과 낙찰하한율을 모두 확인한 경우에만 표시한다. 공고에 예정가격 범위 또는 별도 산식이 있으면 그대로 사용한다. 없고 적용 법령이 구조화 필드 또는 명시 문장에서 확정된 경우에만 국가계약 ±2%, 지방계약 ±3% 일반 범위를 사용할 수 있다.

- 최저 참고값: `기초금액 × 예정가격 최소 사정률 × 낙찰하한율`
- 최고 참고값: `기초금액 × 예정가격 최대 사정률 × 낙찰하한율`

A값, 보험료, 부가세, 단가계약 등 별도 산식의 변수를 모두 확보하지 못하면 단순식을 적용하지 않고 `산식 확인 필요`로 표시한다.

### 10.2 과거 개찰 통계

최근 2년의 유효 결과를 다음 순서로 조회 범위를 넓혀 최소 표본을 확보한다.

1. 같은 세부품명 + 낙찰 방식 + 지역
2. 같은 세부품명 + 낙찰 방식
3. 같은 LED 제품군 + 낙찰 방식

기초금액, 예정가격, 낙찰금액이 모두 양수이고 동일 통화·총액 기준인 최종 낙찰 결과만 유효하다. 취소, 유찰, 재입찰 중간 결과, 단가·복수품목처럼 비교 기준이 다른 결과는 제외한다. 사정률과 낙찰률 각각에 IQR 기반 이상값 제거를 적용하고 중앙값과 25~75 백분위 범위를 사용한다.

- `예상 투찰가 = 현재 기초금액 × 과거 사정률 중앙값 × 과거 낙찰률 중앙값`
- 0~14건: 통계 예측 미제공
- 15~29건: `신뢰도 낮음`
- 30~99건: `신뢰도 보통`
- 100건 이상: `신뢰도 높음`

화면에는 적용한 matching 단계, 분석 기간, 이상값 제외 후 표본 수, 사정률·낙찰률 중앙값과 예상 범위를 표시한다. 이 값은 실제 낙찰가나 낙찰 가능성을 보장하지 않는다.

## 11. 데이터 모델

### 11.1 `tender_company_profiles`

- UUID PK, `singletonKey` unique
- 회사 식별정보, 소재지, 나라장터 등록 여부
- 공급물품, 업종·면허, 기업구분, 직접생산확인, 실적 조건 JSONB
- profile version, 생성·수정 일시

### 11.2 `tender_documents`

- UUID PK, tender FK cascade
- source document identity, 안전한 표시명, mime·format, content hash
- `PENDING | EXTRACTED | PARTIAL | FAILED | UNSUPPORTED` 상태와 안전한 오류 코드
- 정규화한 text/table blocks JSONB, 추출 metadata, 추출 시각
- `(tenderId, sourceDocumentIdentity)` unique
- 원본 binary는 저장하지 않음

### 11.3 `tender_analyses`

- UUID PK, tender FK cascade unique
- 공고·문서·회사 profile·제품군 fingerprint와 analyzer version
- `PENDING | PROCESSING | COMPLETED | PARTIAL | FAILED` 처리 상태
- 참여 상태, nullable 사양 충족도, 비교 가능·충족·불충족·확인 필요 수
- 요구 사양, 인증, 참가 조건, 가격 분석, evidence JSONB
- 점유 token·lease, 마지막 안전한 오류 코드, 분석 시각

### 11.4 `tender_award_results`

- UUID PK
- 출처, 공고번호, 차수·분류번호와 개찰일 unique identity
- 세부품명번호·제품군, 낙찰 방식, 지역
- 기초금액, 예정가격, 낙찰금액을 precision-safe numeric 또는 bigint로 저장
- 사정률·낙찰률 numeric, 최종 낙찰·유찰 여부
- 수집·갱신 시각
- 전체 provider payload, 업체명, 사업자번호, 전체 순위는 저장하지 않음

### 11.5 `tender_award_sync_runs`

- 월별 backfill 또는 증분 구간, cursor
- `RUNNING | SUCCEEDED | PARTIAL | FAILED` 상태
- 조회·저장·제외 건수, lease, 안전한 오류 코드
- 같은 구간·출처의 중복 실행 방지 unique identity

### 11.6 `tender_analysis_reviews`

- UUID PK, tender와 당시 analysis fingerprint FK 또는 immutable reference
- 검토 완료 여부, 2,000자 이하 내부 메모
- 관리자 ID, 검토·수정 시각
- 공고·회사 profile·제품군 변경으로 fingerprint가 달라지면 이전 검토 기록은 보존하되 현재 결과는 다시 `미검토`로 표시

DB 변경 시 기존 migration을 수정하지 않고 신규 migration을 추가하며 `database-schema.md`를 같은 작업에서 갱신한다.

## 12. API

모든 API는 기존 관리자 JWT로 보호한다.

- `GET /tenders/company-profile`: 회사 입찰 자격 조회
- `PUT /tenders/company-profile`: 전체 profile 원자적 저장과 version 증가
- `GET /tenders/:id/analysis`: 상세 분석, 근거, 문서 상태, 가격 통계 조회
- `POST /tenders/:id/analysis`: 실패·부분 분석 또는 최신 fingerprint의 수동 재실행
- `POST /tenders/award-results/backfill`: 최근 2년 백필 시작 또는 중단 지점 재개
- `GET /tenders/award-results/status`: 백필·증분 수집 상태와 유효 표본 현황
- `POST /tenders/:id/review`: 검토 완료 여부와 내부 메모 저장

상세 공고 응답은 큰 문서 text block 전체를 포함하지 않는다. UI에 필요한 근거 snippet과 위치만 반환하고, 원문 문서는 기존 공식 링크로 연다.

## 13. 관리자 UI

### 13.1 상세 모달

기존 760px 공고 상세 모달을 데스크톱 최대 약 1120px로 확장한다. 모바일은 한 열 전체 화면에 가깝게 표시한다.

- 상단: 출처·공고번호·기관·마감과 자동 참여 상태
- 요약 카드: 참여 상태, 사양 충족도와 분석 범위, 요구 인증, 통계 예상 투찰가
- 본문 왼쪽: 참가 조건 목록, 사양·인증 비교표, 근거 문장
- 본문 오른쪽: 기초금액·낙찰하한율·사정률·낙찰률·예상 범위와 표본 신뢰도, 문서별 추출 상태
- 하단: 공식 원문, 다시 분석, 검토 완료

상태는 색상만으로 구분하지 않고 아이콘과 `충족`, `미충족`, `확인 필요` 문구를 함께 사용한다. `82%`처럼 퍼센트만 단독 표시하지 않고 `9개 중 7개 충족, 1개 불일치, 1개 확인 필요`를 병기한다.

### 13.2 회사 입찰 자격 설정

입찰 메뉴 상단의 `회사 자격 설정` 버튼에서 별도 공통 모달을 연다. 자격 유형별 반복 행과 유효기간을 입력하며, 만료 또는 필수값 누락을 저장 전에 표시한다. 저장 뒤 분석 재계산 대상 건수와 진행 상태를 보여준다.

### 13.3 목록

분석이 완료된 공고에는 `참여 추천 | 검토 필요 | 참여 어려움` 배지를 추가한다. 아직 처리되지 않은 공고는 `분석 대기`, 부분 실패는 `일부 확인 필요`로 표시한다. 기존 직접·잠재 관련도 배지는 그대로 유지한다.

## 14. 실패 처리와 일관성

- 출처, 추가 API, 개별 문서와 개찰 통계는 독립 실패 경계를 사용한다. 하나가 실패해도 확보한 근거는 부분 결과로 제공한다.
- 분석 작업은 DB lease와 fingerprint로 중복 실행 및 오래된 작업자의 결과 덮어쓰기를 막는다.
- 변경 공고는 이전 결과를 즉시 확정값으로 보여주지 않고 `재분석 중`과 마지막 성공 시각을 표시한다.
- company profile 또는 제품군 변경 뒤 이전 분석은 stale 상태가 되며 백그라운드에서 재계산한다.
- 외부 API의 429와 일시 5xx·timeout만 제한적으로 재시도한다. 영구 4xx, 권한 없음, 지원하지 않는 문서는 자동 반복하지 않는다.
- 백필은 월 단위 cursor와 advisory lock으로 재시작 가능하게 만들고 운영 공고 수집을 굶기지 않도록 요청 간격과 일일 예산을 분리한다.
- 통계 API가 실패하거나 표본이 부족해도 적합성 분석은 동작하며 통계 카드만 사유와 함께 비활성화한다.

## 15. 환경변수와 운영 설정

새 필수 secret은 추가하지 않는다.

- 기존 `PUBLIC_DATA_SERVICE_KEY` 재사용
- 기존 G2B relay 사용 시 `G2B_RELAY_*`와 Vercel `G2B_DATA_SERVICE_KEY` 재사용
- 나라장터 낙찰정보서비스 base URL은 공식값을 코드 기본값으로 사용하고 선택적 override만 허용
- HWP·PDF 등 문서 추출은 로컬 라이브러리로 실행하며 AI key, OCR key, R2 설정을 요구하지 않음

배포 전에 공공데이터포털에서 같은 계정·키로 `조달청_나라장터 낙찰정보서비스` 활용신청 승인을 받아야 한다. 서비스별 승인이 없으면 같은 key라도 인증 오류가 날 수 있다.

## 16. 테스트 전략

### 16.1 백엔드 단위·계약 테스트

- 나라장터 추가 operation과 K-apt 세부 필드의 공식 fixture 정규화
- 허용 host, redirect, 크기, timeout, magic byte, archive bomb 차단
- PDF/HWP/HWPX/DOCX/XLSX 정상 문단·표, 암호화·손상·이미지 전용·부분 추출 fixture
- 수치 단위, 이상·이하·초과·미만, 인증 별칭, 지역·업종·기업구분·실적 문장 정규화
- hard requirement, 충돌, unknown 우선순위와 evidence 위치
- 단일 제품 조합 기준 사양 충족도, 다품목 합산, 분석 범위와 계산 불가
- 세 상태의 경계값 49/50/79/80과 필수 불충족 우선순위
- 공식 가격 산식, A값 미확보 차단, bigint/numeric 정밀도
- 통계 matching 단계, IQR 이상값 제거, 14/15/29/30/99/100 표본 경계
- backfill cursor 재개, 중복 upsert, advisory lock, provider 부분 실패
- profile·제품·공고 fingerprint 변경과 stale worker 차단
- JWT와 DTO 유효기간·중복 검증

### 16.2 PostgreSQL 통합 테스트

- 신규 migration up/down과 entity discovery
- profile 저장, 분석 lease, 공고 cascade, 개찰 unique identity
- 같은 공고 동시 분석에서 최신 fingerprint 결과만 확정
- 백필 중단 후 재개 시 중복·누락 없음
- 큰 금액의 정밀도와 통계 query 결과

### 16.3 프론트엔드 테스트

- 목록의 분석 상태와 상세 모달 요약
- 사양 분석 범위, 참가 조건, 인증, 근거 snippet, 문서 상태
- 가격 카드의 공식 범위·통계 신뢰도·표본 부족·산식 확인 필요
- 회사 자격 설정 검증과 저장 후 재분석 상태
- 로딩, 부분 실패, 전체 실패, stale, 재실행
- 키보드 focus trap, 상태의 비색상 정보, 모바일 한 열 배치

## 17. 문서화와 출시

- `docs/menus/tenders.md`의 구현 완료, 미구현, 운영 한계를 갱신한다.
- 신규 DB schema와 관계·인덱스를 `database-schema.md`에 기록한다.
- `.env.example`과 `DEPLOYMENT.md`에는 새 필수 환경변수가 없다는 점과 낙찰정보서비스 별도 활용신청만 추가한다.
- 운영 배포 전에 실제 키로 나라장터 추가 상세·낙찰 operation 표본을 검증하되 응답 원문과 key를 로그에 남기지 않는다.
- 최근 2년 백필은 배포와 분리해 관리자가 시작하고 진행률을 확인한다. 백필 완료 전에도 공식 기준 분석은 사용할 수 있다.
- K-apt는 실공고 표본에서 첨부 링크와 낙찰 필드 가용성을 검증하고, 제공되지 않는 항목을 `구현 완료`로 과장하지 않는다.

## 18. 완료 기준

- 나라장터 물품 공고 상세에서 사양 충족도, 인증, 참가 조건, 기초금액과 낙찰하한율을 근거와 함께 확인할 수 있다.
- K-apt는 확보 가능한 조건을 분석하고 미확보 항목을 명확히 `확인 필요`로 표시한다.
- HWP/HWPX 포함 지원 문서의 정상 fixture에서 문단과 표를 추출하며 실패 문서는 안전하게 격리한다.
- 필수 조건과 unknown 우선순위에 따라 세 참여 상태가 결정적으로 계산된다.
- 최근 2년 개찰 결과의 최소 필드만 저장하고 15건 이상일 때만 통계 예상 투찰가를 표시한다.
- 개별 제품을 노출하지 않으며 전체 제품군 기준의 사양 분석 범위가 항상 함께 표시된다.
- 첨부 원본, 전체 투찰 업체, 사업자번호와 provider 원문은 신규 분석 테이블에 저장하지 않는다.
- 새 필수 secret 없이 기존 공공데이터 key를 사용하며, 관리자·외부 입력·다운로드 경계가 테스트된다.

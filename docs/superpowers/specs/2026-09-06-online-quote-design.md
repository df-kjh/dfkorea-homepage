# 온라인 견적 문의 설계안

- 작성일: 2026-09-06
- 상태: 최초 검토용 설계 기록. 이후 구현 및 사진 보관 정책 변경은 아래 대체 설계와 최신 메뉴 문서를 따른다.
- 사용자 확인 완료: 국세청 진위확인에 필요한 대표자명·개업일자를 추가한다. 요청의 ‘이름’은 회사명(상호)으로 해석했다.

## 사진 보관 정책 대체 안내 · 2026-09-06

사진 저장·삭제·보유기간은 [메일 첨부 전용 처리 설계](2026-09-06-quote-email-attachments-design.md)가 이 문서의 기존 저장소 설계보다 우선한다. R2 및 로컬 파일 보관 요구는 폐기하고, PostgreSQL 별도 임시 payload에 메일 첨부용 사진을 보관한다. 접수 전 최대 24시간, 접수 후 `min(견적 정보 보유기간, 7일)`을 적용하며 메일 서비스가 발송을 수락하면 수락 상태와 사진 파일 삭제를 한 트랜잭션으로 반영한다. 수신함의 메일 첨부 사본과 DB 백업의 물리 삭제는 이 즉시 삭제 범위에 포함되지 않는다. 사진을 사용할 수 없는 요청은 사진 없이 발송하지 않는다. 사진 3장, 업로드 식별자, 접수 중복 방지와 입력 흐름은 유지한다.

현행 운영 설정은 [견적 설정 안내](../../quote-setup.md), 기능 현황은 [온라인 견적 메뉴](../../menus/quote.md)를 따른다.

## 목적과 범위

방문자가 회원가입 없이 기업 정보를 입력하고 자사 제품 또는 직접 작성한 사양으로 견적을 요청한다. 접수 정보를 저장하고 `kymkjh2002@dfkorealed.com`으로 견적 요청서를 발송한다. 단가 자동 산정, 고객에게 확정 견적서 자동 발급, 실시간 상담원 채팅은 이번 범위에 포함하지 않는다.

## 현재 구조와 선택한 방식

- Nuxt 4 / Vue 3 프론트엔드, NestJS / TypeORM / PostgreSQL 백엔드.
- `src/app.vue`에 공개 페이지 공통 맨 위로 버튼이 있다. 스크롤 300px 이후 표시한다.
- 홈의 `CtaSection.vue`는 전화·이메일 선택 다이얼로그를 제공한다.
- 제품 검색은 현재 제품명·카테고리로 서버에서 필터링하고 페이지를 나눈다. 모델명 검색과 사양 필터가 필요하다.
- 제품의 `power`, `colorTemp`, `certifications`는 배열이다. 필터 일치가 실제 판매 가능한 모든 사양 조합을 보증하지는 않는다.
- 입찰 기능에 NAVER WORKS 사용자 OAuth·메일 전송·실패 분류 코드가 있다. 현재 전송 인터페이스에는 첨부 파일이 없다.
- 기존 제품 업로드는 공개 이미지 URL을 반환한다. 문의용 사진은 별도 비공개 DB 임시 영역에서 처리한다.

검토한 화면 방식:

1. **3단계 팝업(권장):** 기업 정보 → 제품 선택 → 요청 확인. 작은 창에서 긴 입력을 나누고 이전 입력을 유지한다.
2. 단일 긴 폼: 한 번에 훑어보기 좋지만 모바일과 여러 제품 입력에서 스크롤이 길어진다.
3. 한 항목씩 묻는 대화형 폼: 친근하지만 사양 비교와 수정, 복수 제품 입력에 왕복이 많다.

접수 저장 후 메일을 발송하는 방식을 선택한다. 메일만 보내는 방식보다 저장 구조가 추가되지만 전송 장애에도 문의가 남고 중복 접수를 제어할 수 있다.

## 진입과 팝업

- 공개 페이지 우하단에 파란색 `온라인 견적` 버튼을 항상 표시한다. 관리자 화면은 제외한다.
- 맨 위로 버튼 위에 12px 간격으로 배치한다. 맨 위로 버튼이 숨겨져도 견적 버튼 위치가 튀지 않도록 기준 위치를 유지한다.
- 데스크톱: 오른쪽 24~32px, 기본 너비 440px, 최대 높이 `min(720px, 100dvh - 160px)`. 버튼 바로 위에서 우하단을 기준으로 약 180ms 동안 열린다. 작은 높이에서는 가용 화면을 우선한다.
- 팝업의 헤더, 단계 표시, 하단 이전/다음 버튼은 고정하고 본문만 스크롤한다. 페이지 전체를 어둡게 덮지 않는 비모달 창이다.
- 640px 미만: 전체 너비의 하단 시트, 높이 최대 `100dvh`, 안전 영역·가상 키보드 대응. 배경 스크롤 차단과 포커스 가두기를 적용한다.
- 닫기/ESC는 최소화이며 같은 탭에서 제품·수량·폼·사진을 메모리에 보관한다. 새로고침 시 초기화하며 개인정보를 localStorage에 저장하지 않는다.
- 닫으면 열었던 버튼으로 포커스를 돌린다. 다시 열면 작성 단계로 복귀한다. 동작 줄이기 설정이면 확대·이동 효과를 생략한다.
- 홈의 문의 방법 선택 화면에도 `온라인 견적`을 추가해 동일한 창을 연다. 제품 상세에도 `견적에 담기`를 추가해 해당 제품을 미리 담고 기업 정보 단계부터 진행한다.

## 1단계: 기업 정보

| 항목 | 필수 | 규칙 |
| --- | --- | --- |
| 회사명(상호) | 예 | 사업자등록증의 상호. 최대 100자 |
| 사업자등록번호 | 예 | 숫자 10자리, 표시 형식 000-00-00000. 형식 확인은 진위확인과 구분 |
| 대표자명 | 예 | 담당자와 별개. 국세청 진위확인용, 최대 100자 |
| 개업일자 | 예 | 사업자등록증 기준 날짜. 국세청 진위확인용 |
| 담당자명 | 예 | 실제 회신받을 사람, 최대 50자 |
| 이메일 | 예 | 회신 주소. 앞뒤 공백 제거, 서버에서도 형식 검증 |
| 전화번호 | 아니오 | 선택 입력임을 라벨에 표시, 입력된 경우에만 검증 |

- 사업자 정보 그룹에 `사업자 정보 확인` 버튼을 둔다. 확인 전 수집·이용 안내와 필수 동의를 제공하고, 최종 확인에서도 동의 내용을 열어볼 수 있다.
- 검증 목표는 **사업자번호와 입력 상호를 포함한 등록정보의 일치**이다. 번호 체크섬, 정상 영업 상태, 대표자 일치만으로 회사명 확인 완료라고 표시하지 않는다.
- 공식 안내로 확인된 사항: 국세청 진위확인은 번호·개업일자·대표자명 등으로 비교하고, 번호 단독 상태조회는 휴폐업·과세유형 등의 정보를 반환한다.
- 구현 착수 시 공식 API 명세에서 상호 필드 `b_nm`과 ‘요청항목이 전부 일치’ 조건을 확인했다. `b_no`, `start_dt`, `p_nm`, `b_nm`을 보내며 진위 결과 `valid: 01`과 정상 영업 상태를 모두 확인한다. 정상 번호에 틀린 상호를 넣었을 때 불일치하는 계약 테스트를 포함한다. 실제 운영 키를 이용한 정상/불일치 확인은 운영 연결 때 수행한다.
- 대표자·개업일자 추가 없이 원래 필드만 유지하려면 사업자번호로 상호를 조회할 수 있는 외부 기업정보 서비스의 제공 범위·계약을 먼저 확인해야 한다. 서비스와 가격은 아직 선택하지 않았다.
- 정상 일치 / 불일치 / 형식 오류 / 조회 장애 / 미등록 / 휴폐업을 구분한다. 기본안에서는 등록정보 일치 및 정상 영업 확인 시에만 온라인 제출을 허용한다.
- API 장애 시 확인 완료로 우회하지 않는다. 입력은 유지하고 재시도와 기존 전화·이메일 문의를 안내한다. 신규 개업 정보 반영 지연도 안내한다.
- 회사명·번호·대표자·개업일자 중 하나라도 수정되면 인증을 해제한다.
- 검증은 서버에서 수행한다. 서버가 발급한 불투명한 검증 토큰을 익명 작성 세션·입력 정보 해시·30분 만료에 연결하고 제출 시 다시 확인한다. 프론트엔드의 `verified: true`를 신뢰하지 않는다.
- 이 검증은 입력된 등록정보의 일치 확인이며, 담당자의 재직·대표권·이메일 소유권 인증을 의미하지 않는다.

## 2단계: 제품 및 수량

### 자사 제품 검색

- 제품명·모델명 검색. 입력 300ms 후 검색하고 오래된 요청 응답은 무시한다.
- 기본 필터: 카테고리, 소비전력(W), 인증. 펼침 영역에 색온도(K), 옵션을 제공한다.
- 서로 다른 필터는 AND. 같은 필터의 여러 값은 OR. 값이 없는 제품은 해당 사양을 요구한 검색에서 제외한다.
- 모든 조건을 전체 제품에 적용한 뒤 페이지를 나눈다. 현재 읽은 페이지만 추가 필터링하지 않는다.
- 서버의 실제 카탈로그에서 필터 선택지를 만든다. 선택 조건 칩, 조건 초기화, 결과 수, 더 보기, 로딩·실패·결과 없음 상태를 제공한다.
- 제품 행에 이미지·제품명·모델명·와트·인증과 `담기` 버튼을 표시한다.
- 담을 때 희망 와트·색온도·옵션을 선택하거나 `상담 후 결정`을 허용한다. 제품 자체가 가진 복수 사양을 하나로 임의 결정하지 않는다.
- 수량은 필수 정수 1~999,999개. 요청당 최대 20개 품목. 같은 제품·같은 선택 사양은 수량을 합치고 다른 사양은 별도 행으로 담는다.
- 제품에 저장된 인증 표시와 고객이 요구하는 인증을 구분한다. 개별 와트·인증 조합의 실제 공급 가능 여부는 담당자 검토 대상이다.
- 담은 목록에서 수량 수정·삭제를 제공한다. 기존 카탈로그 항목과 직접 입력 항목을 함께 제출할 수 있다.
- 검색 결과가 없을 때 `조건 초기화`와 `원하는 사양 직접 입력`을 표시한다. 조회 실패를 검색 결과 없음으로 취급하지 않는다.
- 직접 입력 진입 버튼은 검색 결과가 있을 때도 유지한다.

### 원하는 사양 직접 입력

- 필수: 제품 종류/이름, 수량, 요구 사양 설명(최대 2,000자).
- 선택: 소비전력(W), 색온도(K), 규격/크기, 필요한 인증, 기타 설치 조건. 모르는 항목은 비워둘 수 있다.
- 각 항목은 `직접 입력` 배지로 카탈로그 제품과 구분한다.
- 예시 사진은 **견적 요청 전체에서 최대 3장**을 기본안으로 한다. 사진마다 직접 입력한 품목에 연결한다.
- JPEG·PNG·WebP, 원본 장당 최대 5MB. 미리보기·개별 삭제·교체 제공. 4장째 선택 시 기존 사진을 보존하고 한도를 안내한다.
- 원본 파일은 전송 전까지 브라우저 메모리에 유지한다. 제출 시 서버가 확장자·MIME·실제 이미지 디코딩·픽셀 수를 검증한다. 최대 40MP, 최대 변 1,920px로 축소, 메타데이터를 제거한다.
- 메일 첨부용 JPEG/PNG로 변환해 장당 2MB, 전체 6MB 이하를 목표로 압축한다. 한도 달성이 불가능하면 해당 파일 재선택 안내.
- 공개 제품 이미지 버킷/URL을 재사용하지 않는다. PostgreSQL의 별도 임시 payload에 세션 소유권을 연결한다. 접수 전 최대 24시간, 접수 후 `min(견적 정보 보유기간, 7일)`만 보관하며 메일 서비스의 발송 수락 시 서버 사진 파일을 삭제한다. 수신 메일의 첨부 사본은 수신함 보유 정책을 따른다.

## 3단계: 요청 확인

- 확인된 회사명·사업자번호, 담당자 연락처, 제품별 선택 사양·수량, 사진 개수를 표시한다.
- 기업 정보와 제품 목록에 `수정`을 제공한다. 단계 이동 시 입력을 보존한다.
- 추가 요청사항(선택, 최대 2,000자), 희망 납기일(선택)을 제공한다.
- 수집·이용 동의 상태 및 안내 전문을 확인할 수 있다. 안내에는 목적, 필수/선택 항목, 보유기간, 거부 시 이용 제한을 명시한다. 견적 정보의 운영 보유기간은 회사 방침과 맞춰 출시 전에 확정하며, 사진 파일의 임시 보관기간과 별도로 안내한다.
- 최종 버튼은 `견적 요청 보내기`이다. 처리 중 중복 클릭을 막고 `접수 중…`을 표시한다.
- 제출 필수 조건: 검증 유효, 기업 필수 정보, 한 개 이상 유효 품목, 파일 처리 완료, 필수 동의.
- DB 저장 성공 시 접수번호와 `견적 요청이 접수되었습니다`를 표시한다. 메일 서버 수락이나 최종 수신함 배달을 접수 성공과 혼동하지 않는다.
- 저장 실패·시간초과 시 입력과 재시도 키를 유지한다. 재시도 때 같은 접수번호를 반환하도록 중복을 막는다.

- 사진 최대 3장을 실제 첨부한다. 기존 전송 어댑터에 Base64 첨부 배열을 추가한다. 고객 회신 주소는 본문에 클릭 가능한 이메일 링크로 포함한다. Reply-To 헤더는 송신 API 지원 확인 후에만 적용한다.
- 고객에게 보내는 접수 확인 메일은 이번 기본 범위에 추가하지 않는다.
- 접수와 발송 대기 레코드는 하나의 DB 트랜잭션으로 기록한다. 업로드 준비 완료 후 참조를 붙이고, 실패 시 미연결 객체를 정리한다.
- 별도 작업자가 발송 대기 레코드를 점유해 전송한다. 제공자가 수락한 202는 `PROVIDER_ACCEPTED`이며 최종 배달 보장은 아니다.
- 명확한 일시적 거절은 1/5/30분 후 최대 3회 재시도한다. 영구 거절은 실패 처리한다.
- 네트워크 시간초과·수락 여부 불명·작업자 비정상 종료는 `DELIVERY_UNCERTAIN`으로 보관한다. 수락 여부가 불명확한 요청을 자동 재발송해 중복 메일을 만들지 않는다.
- 운영자는 인증된 제한용 조회·수동 재전송 도구로 실패/불명 접수를 확인한다. 수동 재전송은 중복 가능성을 표시하고 이력을 남긴다. 공개 고객 화면에는 운영 도구를 노출하지 않는다.
- 운영 도구의 실패·미처리 건수는 서버 모니터링에 연결한다. 문의 DB 기록을 메일 성공 여부와 무관하게 보존한다.

## 구성과 데이터 변경 계획

프론트엔드:

- `components/common/`: 재사용 버튼·입력 필드·사양 필터·파일 선택 UI. 기존 공통 컴포넌트를 먼저 확인해 확장한다.
- `components/quote/`: QuoteLauncher, QuotePanel, CompanyStep, ProductStep, ProductPicker, CustomProductForm, QuoteItemList, ReviewStep, SuccessState.
- `composables/useQuoteDraft.ts`: 단계·폼·제품·사진·중복 요청 키의 탭 메모리 상태.
- 제품 검색 조건은 제품 목록과 견적 선택기가 공유한다. 라우트 이동에도 전역 작성 상태를 유지한다.

백엔드:

- `quotes/`: 요청 DTO, 세션·검증·접수·비공개 파일 서비스, 요청서 템플릿, 발송 작업자.
- `business-verification/`: 공급자별 응답을 VERIFIED/MISMATCH/UNAVAILABLE 등 공통 상태로 변환.
- `mail/`: 기존 NAVER WORKS 인증·전송 코드를 공통화한다. 입찰 전용의 집계·스케줄·수신자 로직은 입찰 모듈에 둔다.

예정 API:

- `POST /quotes/sessions`: 짧은 수명의 익명 작성 세션. SameSite/HttpOnly 보안 쿠키 또는 동등한 세션 바인딩.
- `POST /quotes/business-verifications`: 기업 정보 검증과 만료 토큰 반환.
- `GET /products?...`: 기존 검색에 모델명·사양 조건 추가. 미지정 시 기존 응답 계약 유지.
- `GET /products/filter-options`: 실제 데이터의 사양 선택지. `GET /products/:id`보다 우선 등록.
- `POST /quotes/attachments`: 검증된 작성 세션의 제한된 비공개 파일 업로드. multipart `file`과 사진별 고정 UUID `clientAttachmentId`를 전송한다. 같은 세션·식별자·파일의 재시도는 같은 첨부를 반환하고 파일 내용 변경은 거절한다. 교체 사진은 새 식별자를 사용한다.
- `DELETE /quotes/attachments/:id`: 같은 작성 세션의 제출 전 파일만 삭제.
- `POST /quotes`: 검증 토큰, 작성 세션, 중복 요청 키, 품목, 첨부 ID를 검증하고 접수.
- 관리자 인증 아래 제한된 접수 조회/발송 재처리 API. 일반 사용자에게 접수번호만으로 개인정보를 조회하는 API는 제공하지 않는다.

예정 테이블:

| 테이블 | 주요 내용 |
| --- | --- |
| quote_sessions | 만료된 익명 작성 세션 및 제한 카운터 |
| quote_business_verifications | 세션·입력 해시·확인 결과·확인시각·만료시각, 짧은 수명의 검증 토큰 해시 |
| quote_requests | 비추측 접수번호, 세션별 유일 중복 요청 키, 회사/담당자 스냅샷, 동의 버전/시각, 요청사항·납기 |
| quote_items | 카탈로그/직접 입력 구분, 제품 참조(삭제 시 null), 모델·사양 스냅샷, 선택 사양, 수량 |

제품·사양 스냅샷은 서버가 카탈로그를 다시 읽어 작성한다. 고객 입력 제품명이나 인증을 그대로 카탈로그 사실로 저장하지 않는다. 접수 후 원제품 변경·삭제에도 요청 당시의 내용은 유지한다.

공개 입력 보호는 서버에서 시행한다. 길이·품목수·파일수·용량·형식 검증, IP/세션별 호출 제한, Origin 검증, 메일 HTML 이스케이프, 임의 URL 첨부 다운로드 차단을 포함한다. 로그에는 인증키·원문 개인 정보·사진을 남기지 않는다.

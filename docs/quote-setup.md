# 온라인 견적 운영 설정

견적 사진은 메일 첨부로 전달한다. 압축된 사진을 기존 PostgreSQL에 잠시 보관하므로 **견적용 R2 버킷·접근 키·로컬 사진 저장 경로를 새로 설정할 필요가 없다.** 제품·게시글 이미지의 기존 저장 설정은 별도 기능이다.

## 최소 설정

**기존 입찰 메일·홈페이지·DB가 정상이고 `NTS_SERVICE_KEY`도 등록했다면, 견적 전용 환경변수를 추가할 필요가 없다.** 최신 코드 배포 전에 견적/payload 마이그레이션을 적용한다.

| 항목 | 기본 동작 |
| --- | --- |
| IP 요청 제한 | 기존 `JWT_SECRET`에서 견적 IP 해시용 키를 파생한다. 원본 IP는 저장하지 않으며 시간당 제한을 유지한다. |
| 허용 주소 | 기존 `CORS_ORIGIN`의 정확한 주소 목록을 사용한다. 없으면 `PUBLIC_SITE_URL`의 Origin을 사용한다. 둘 다 없거나 주소가 잘못되면 요청을 허용하지 않는다. |
| 견적정보 보유기간 | 기본 365일. 사진은 미제출24시간·제출후최대7일 또는 메일발송수락까지 임시 보관한다. |
| 메일·정리 작업자 | `NODE_ENV=production`에서 자동 실행한다. 개발·테스트에서는 기본 정지한다. |
| 외부 연결 | 등록된 `NTS_SERVICE_KEY`와 기존 NAVER WORKS 사용자 인증·DB 연결을 재사용한다. 견적용 R2 설정은 없다. |

프론트엔드는 기존 `VITE_API_BASE_URL`, 백엔드는 기존 `PUBLIC_SITE_URL`·`CORS_ORIGIN`·DB·JWT·NAVER WORKS 설정을 유지한다. 수신자는 `kymkjh2002@dfkorealed.com`이다.

## 선택 설정

기본값을 바꿔야 할 때만 `QUOTE_RETENTION_DAYS`, `QUOTE_ALLOWED_ORIGINS`, `QUOTE_IP_HASH_SECRET`, `QUOTE_WORKER_ENABLED`를 지정한다. 이미 지정했다면 해당 값이 우선한다. **특히 기존 `QUOTE_WORKER_ENABLED=false`가 남아 있다면 삭제해야 운영 기본 자동 실행을 사용한다.** 개발에서 실제 메일 발송을 시험하려면 명시적으로 `true`를 설정한다.

회사 정책에 따라 보유기간을 바꾸면 동의문과 실제 정리에 함께 반영된다. 별도 IP키 없이 `JWT_SECRET`을 교체하면 IP 요청 제한 해시도 달라져 현재 시간대의 횟수가 새로 집계된다. 모든 서버는 같은 JWT 키를 사용한다.

`TRUST_PROXY_HOPS`는 실제 신뢰할 프록시 경로를 확인한 경우에만 설정한다. 보안에 영향을 주므로 환경변수를 줄이기 위해 프록시를 자동으로 신뢰하지 않는다.

변수 예시는 [백엔드 환경 예시](../dfkorea-backend/.env.example), 테이블 구조는 [DB 스키마](../database-schema.md)를 따른다. 운영에서는 마이그레이션을 먼저 적용하고 서버를 시작한다. 이 설정 간소화 자체는 추가 DB 마이그레이션을 요구하지 않는다.

## 사진 보관과 장애 처리

- 사진은 최대 3장이다. 원본 장당 5MiB·40MP 이하의 정지 JPEG·PNG·WebP를 받고, 검증·축소·메타데이터 제거 후 메일용 사진을 장당 2MiB·전체 6MiB 이하로 처리한다.
- 접수하지 않은 사진은 최대 24시간, 접수한 사진은 접수 후 `min(QUOTE_RETENTION_DAYS, 7일)`까지만 임시 보관한다. 견적 내용과 사진 첨부 기록의 보유기간은 `QUOTE_RETENTION_DAYS`로 별도 관리한다.
- NAVER WORKS가 발송을 수락한 상태와 서버 사진 파일 삭제를 한 DB 트랜잭션으로 반영한다. 이후 사진은 수신 메일의 실제 첨부에서 확인하며 서버에서 다시 내려받거나 재전송할 수 없다. 발송 수락은 최종 수신함 배달 보장과 다르다.
- 명확한 일시적 거절은 사진을 유지해 재시도한다. 수락 여부가 불명확하면 자동으로 다시 발송하지 않는다. 사진이 만료되거나 누락되면 사진을 뺀 메일을 보내지 않고 발송·수동 재전송을 거절한다. 관련 오류와 미처리 상태를 운영자가 확인해야 한다.
- 서버 사진 삭제는 수신 메일 첨부 사본이나 DB 백업의 즉시 물리 삭제를 의미하지 않는다. 수신함과 백업의 접근·보유·삭제 정책을 별도로 관리한다.
- 이전 R2 방식이 이미 운영 중이라면 전환 전에 기존 작업자를 중지하고 발송 대기 건을 정리한다. 기존 R2 객체는 자동 이관·삭제하지 않으며 별도 처리가 필요하다. 새 임시 사진 데이터가 없는 요청은 사진 없이 발송하지 않는다. 아직 배포하지 않았다면 이 전환 작업은 필요 없다.

운영 배포 전 실제 메일의 사진 첨부 열기, 발송 수락 후 서버 사진 삭제, 실패·만료 시 사진 없는 발송 차단을 승인된 정보로 검증한다. 코드와 로컬 테스트 완료만으로 운영 연결 완료라고 표시하지 않는다.
